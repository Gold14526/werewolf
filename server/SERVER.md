# 联机服务

运行 `npm start`（Node.js 22.13 或更新版本；无第三方运行依赖），打开 `http://localhost:3000`。同一个服务同时提供页面和游戏 API。同一局所有玩家必须连接同一个服务实例。

服务默认使用 Node 内置 SQLite，将状态保存到项目的 `data/moonwolf.sqlite`。可通过 `DATABASE_PATH` 指定数据库文件。正式部署必须使用持久磁盘或 Docker 数据卷；重启、更新镜像或重新部署时继续挂载同一份数据库。仅把源码上传 GitHub 不会把实时对局数据保存到 GitHub。

## GitHub Pages + 独立后端

GitHub Pages 只能托管静态前端。将此仓库部署到支持 Node.js 或 Docker 且提供持久磁盘的服务器，再将仓库变量 `API_BASE_URL` 配置成后端的 HTTPS 根地址，并重新发布 Pages。后端设置示例：

```sh
ALLOWED_ORIGINS=https://gold14526.github.io
PORT=3000
HOST=0.0.0.0
DATABASE_PATH=/var/data/moonwolf.sqlite
```

`/var/data` 必须是已挂载的持久磁盘目录。`ALLOWED_ORIGINS` 可填多个逗号分隔的精确 origin，不含路径。例如 GitHub Pages 网站 `https://gold14526.github.io/werewolf/` 对应 `https://gold14526.github.io`。同源访问默认允许；跨域来源必须显式配置。浏览器通过 Bearer token 恢复会话，token 不放入 URL。

附带 `render.yaml` 使用原生 Node.js 24、付费 `starter` 实例和挂载到 `/var/data` 的 1 GB 持久磁盘；构建命令为 `npm ci --omit=dev`，启动命令为 `node server/index.mjs`，`DATABASE_PATH` 为 `/var/data/moonwolf.sqlite`。手动部署时也必须添加磁盘。实际套餐和费用以平台创建页面为准，由账号所有者确认并购买；配置文件不表示服务已经开通。免费易失磁盘和未挂载持久磁盘的付费实例都不满足数据保留要求。

使用自己的服务器时，可运行 Docker：

```sh
docker build -t moonwolf .
docker volume create moonwolf-data
docker run --name moonwolf --restart unless-stopped \
  -p 127.0.0.1:3000:3000 \
  -v moonwolf-data:/var/data \
  -e DATABASE_PATH=/var/data/moonwolf.sqlite \
  -e ALLOWED_ORIGINS=https://gold14526.github.io \
  moonwolf
```

也可使用仓库的 `compose.yaml`。上述命令和 Compose 均只绑定 `127.0.0.1:3000`，公网访问需设置 HTTPS 反向代理。保留原数据卷再升级镜像；不要删除数据卷。数据库目录应仅供服务账号读写，不要把数据库、会话和备份提交到公开仓库。

## 保存与重启恢复

SQLite 保存完整的房间和游戏状态，包括身份、夜间技能、当前阶段、投票、会话、聊天、历史和排行榜。每次成功 API 操作及每秒游戏计时推进均先提交数据库事务，再返回成功或发布该状态。数据库使用 WAL 与 `synchronous=FULL`；记录版本用于检测冲突。若提交失败或发生状态冲突，当前实例停止接受游戏操作并返回 503，修复存储后需重启，避免把未保存的动作报告为成功。

启动时恢复最后一次已提交的状态，并冻结服务停机期间的计时：阶段按保存时的剩余时间继续，至少保留 30 秒操作时间；会话和房间获得 2 分钟重连宽限。停机时长不会直接算作玩家离线或房间闲置，从而清空正在恢复的对局。历史行动与聊天的原始时间不改写。玩家在原标签页保有会话 token 时可以刷新并回到原座位。

正常运行期间仍遵循游戏计时与清理规则：等待房间中的玩家超过 2 分钟无请求会被移除；活跃对局由计时器继续推进；30 分钟无人访问的房间自动删除；会话最长空闲 24 小时。重启不是清空原因，但持久化不代表无限期保留所有历史，也不能恢复已按规则清理的数据。

本实现只运行一个实例。不要横向扩容为多个独立实例，也不要让多个进程直接共用同一个 SQLite 文件。多实例部署需要另行实现独立持久数据库、并发控制和统一房间路由。部署容量上限为 1000 个房间和 10000 个会话；实际承载能力还取决于主机资源与数据库写入量。

请定期备份数据库，并在独立环境验证恢复。持久磁盘可跨进程重启和镜像更新保存数据，但不能代替磁盘损坏、误删除或账号资源被删除后的备份。SQLite 使用 WAL，运行中直接复制单个数据库文件不构成可靠备份。使用本项目的在线备份命令：

```sh
npm run backup -- /absolute/new-backup.sqlite
```

命令默认读取项目的 `data/moonwolf.sqlite`；若服务设置了 `DATABASE_PATH`，备份进程也须设置相同变量。目标必须为绝对路径且文件尚不存在，命令拒绝覆盖旧备份，并检查生成的 SQLite 文件。Render 示例：

```sh
DATABASE_PATH=/var/data/moonwolf.sqlite npm run backup -- /var/data/backups/new-backup.sqlite
```

每次使用新的目标文件名。备份成功后，将文件另存到独立的外部存储；同一块持久磁盘内的备份不能防止该磁盘丢失。恢复操作应先停止服务，保留原数据库目录作为回退，再把经过检查的备份放到 `DATABASE_PATH` 指定的位置后启动。

## 房间与身份

房号由密码学随机数生成，范围为 `100000`–`999999`，生成时检测现有房间冲突。房号是邀请凭据，私人房间不会出现在公开房间列表。匹配固定采用 12 人默认标准配置；匹配者自动准备，12 人到齐自动开始。自定义房间由房主在满员且全员准备后开始。

服务端独立验证身份、角色权限、目标、阶段与投票，只向每位玩家发送其可见身份与私有信息。客户端不能通过修改页面获得其他玩家的隐藏身份。每局游戏进行中不允许主动退出房间；在会话有效且保留原 token 时可重新连接。

这里不是跨设备账号系统。昵称不是唯一账号，清空浏览器会话或换设备后不能凭昵称找回原身份。服务器重启不会要求重新创建身份，但客户端仍需提供原 token。

## 历史记录、排行榜与聊天

`GET /api/history` 返回最近 100 场内当前用户可访问的已结束对局；公开房间记录可由所有登录用户阅读，私人房间记录仅对参与者可见。`GET /api/history/:code` 返回复盘快照，对局结束后身份及狼人密聊公开给有权阅读该记录的用户。`GET /api/stats` 返回已保存的胜场、局数和百分比胜率；每局只结算一次。上述记录保存在 SQLite，服务重启后继续保留，历史记录仍受最近 100 场上限约束。

公开聊天仅允许轮到发言或遗言的玩家发送；夜间狼人密聊仅允许当前仍存活的狼人发送，内容在对局结束前不发给好人。等待大厅及对局结束后可自由公开发言。消息最多 500 字，单房间按发送顺序保留最近 2000 条（公开聊天与狼人密聊合计）。`POST /api/session` 携带已有 Bearer token 可恢复身份，等待阶段可修改昵称，对局中不能改名。
